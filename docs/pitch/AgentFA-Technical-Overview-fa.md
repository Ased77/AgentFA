# AgentFA — نمای فنی

**این پروژه چه کار می‌کند و چطور کار می‌کند**
نسخه ۱.۰ · مهر ۱۴۰۵

> سند کوتاه فنی برای مهندس/سرمایه‌گذار فنی. هر بخش یک اسلاید است. تمرکز روی «چه چیزی ساخته شده» و «چطور کار می‌کند»، نه بازار و مالی.
>
> **اگر وقت کم است:** اسلایدهای ۱، ۳، ۴، ۸ و ۱۰ را بگویید؛ بقیه، جزئیات پشتیبان‌اند.

---

## اسلاید ۱ — در یک جمله

**AgentFA یک بازار و موتور اجرای ایجنت‌های تخصصی فارسی است.**

کاربر یک ایجنت (مثلاً «استراتژیست کمپین») می‌خرد، با پرسونای همان ایجنت چت می‌کند، پاسخ به‌صورت استریم می‌آید و مصرفش بر اساس توکن یا زمان از کیف پولش کسر می‌شود. همهٔ پول، مالکیت، مصرف و کلید مدل سمت سرور است.

۲۶۴ ایجنت · ۱۸ حوزه · ۱۶ جدول · ۷ گروه API · ۵۸ تست خودکار

| مؤلفه | فناوری |
| --- | --- |
| فرانت | React 19 · Vite 8 · Tailwind v4 · React Router 7 |
| API | Fastify 5 · TypeScript · Zod |
| داده | Postgres · Prisma 6 (بدون باینری موتور پرس‌وجو) |
| مدل | ارائه‌دهندهٔ سازگار با OpenAI، کلید سمت سرور |
| استقرار | Vercel: SPA استاتیک + یک Function برای `/api` |
| گیت‌وی AI | FastAPI + LiteLLM (سرویس جدا، آمادهٔ اتصال) |

## اسلاید ۳ — معماری

```
[مرورگر]  SPA — React 19 / Vite
    │  /api  (same-origin، کوکی httpOnly)
    ▼
[Fastify API]  ← یک Vercel Function
    ├── Postgres            (Prisma؛ همهٔ state)
    ├── درگاه پرداخت        (زرین‌پال / استرایپ)
    ├── پیامک               (OTP، کاوه‌نگار)
    └── ارائه‌دهندهٔ مدل     (کلید رمزنگاری‌شده، سمت سرور)
```

**نکته‌های معماری:**
- **یک دامنه:** SPA و API در یک پروژهٔ Vercel؛ بدون CORS و با کوکی first-party.
- **یک دیتابیس:** همهٔ state سمت سرور (کاربر، کیف پول، مالکیت، مصرف، تراکنش، کاتالوگ، پرسونا) در Postgres.
- **بدون فایل در زمان درخواست:** کاتالوگ در build ساخته و seed می‌شود؛ برای سرورلس امن است.
- **کلید مدل هرگز به مرورگر نمی‌رسد:** فقط سمت سرور رمزگشایی می‌شود.

## اسلاید ۴ — چرخهٔ یک درخواست چت

```
POST /api/chat/stream
  { agentId, conversationId?, message, history[], lang }
        │
        ▼
۱. نشست → کاربر        (کوکی httpOnly، توکن هش‌شده)
۲. محدودیت نرخ         (۲۰/دقیقه · ۱۰۰/ساعت · ۵۰۰/روز)
۳. مالکیت ایجنت        (یا ۳ پیام پیش‌نمایش رایگان)
۴. تنظیمات مدل + کیف پول
۵. بارگذاری پرسونا     (فقط سمت سرور)
۶. تعیین بودجه         (پیش‌نمایش ۴٬۰۰۰ توکن/۱۲۰ ثانیه؛ مشتری: ماندهٔ کیف پول)
۷. فراخوانی مدل        (system + ۱۰ نوبت تاریخچه)
۸. استریم پاسخ         (SSE: delta / done / error)
۹. اندازه‌گیری مصرف     (توکن یا ثانیه)
۱۰. کسر + ثبت          (تراکنش دیتابیس: Wallet + UsageEvent + Message)
```

**جزئیات مهم:**
- اگر پاسخ از بودجه بیشتر شود، استریم قطع و پاسخ «truncated» علامت می‌خورد.
- قطعی سکوت ۳۰ ثانیه‌ای در صورت توقف ارائه‌دهنده.
- مصرف در یک تراکنش دیتابیس کسر می‌شود؛ پیام و شمارندهٔ گفت‌وگو هم همان‌جا ذخیره می‌شوند.

## اسلاید ۵ — مدل داده

| گروه | جدول‌ها | نقش |
| --- | --- | --- |
| هویت | `User` · `Session` · `LoginCode` | شمارهٔ موبایل، نشست، کد یک‌بارمصرف |
| پول | `Wallet` · `Transaction` · `Entitlement` · `UsageEvent` | موجودی، تراکنش، مالکیت، ریز مصرف |
| محتوا | `Division` · `Agent` · `Persona` · `PreviewUsage` | کاتالوگ و متن کامل پرسونا |
| گفت‌وگو | `Conversation` · `Message` | تاریخچهٔ چت و مصرف هر نوبت |
| عملیات | `ProviderConfig` · `RateLimit` · `ClientError` | تنظیمات مدل، محدودیت نرخ، خطای مرورگر |

**قواعدی که در schema قفل شده‌اند:**
- قیمت در `Agent.price` است؛ خرید، قیمت را از سرور می‌خواند و به کلاینت اعتماد نمی‌کند.
- `Entitlement` روی `(userId, agentId)` یکتاست؛ خرید دوباره، رکورد را به‌روز می‌کند.
- `refId` و `providerToken` یکتا هستند؛ یک پرداخت نمی‌تواند دو سفارش را تسویه کند.
- `Persona` جدا از `Agent` است تا متن کامل، فقط برای مالک ارسال شود.

## اسلاید ۶ — خط تولید کاتالوگ

```
divisions.json + <division>/*.md
        │  (frontmatter: name, description, prompts…)
        ▼
generate-catalog.mjs
        │
        ├── src/data/catalog.generated.ts   (264 ایجنت، انگلیسی)
        ├── src/data/divisions.generated.ts (18 حوزه)
        └── featured.generated.ts           (۱۲ ایجنت صفحهٔ اصلی)
        ▼
export-personas.mjs → server/content/seed.json
        ▼
seed-content.ts → Postgres (Agent + Persona + Division)
```

- تولید **در build** انجام می‌شود، نه در زمان درخواست؛ مناسب سرورلس.
- ترجمهٔ فارسی در `fa-agents.ts` نگهداری می‌شود؛ بررسی خودکار مطمئن می‌شود UI انگلیسی، متن فارسی نشان ندهد.
- چک‌های `check:catalog` و `check:routes` جلوی رگرسیون محتوا و مسیرها را می‌گیرند.

## اسلاید ۷ — کیف پول و اندازه‌گیری مصرف

| مفهوم | پیاده‌سازی |
| --- | --- |
| دو موجودی | `tokenBalance` و `timeBalanceSeconds` |
| حالت اندازه‌گیری | هر ارائه‌دهنده/ایجنت: `tokens` یا `time` |
| دوره | ۳۰ روز؛ به‌روزرسانی تنبل روی خواندن/کسر، بدون cron |
| بازگردانی سهمیه | `balance = max(balance, allowance)` — سهمیه برمی‌گردد، خرید اضافه حفظ می‌شود |
| کسر | داخل `prisma.$transaction`: خواندن کیف پول، بررسی کفایت، کاهش، ثبت `UsageEvent` |
| پیش‌نمایش | شمارندهٔ `PreviewUsage` سمت سرور؛ با پاک‌کردن مرورگر ریست نمی‌شود |

**چرا این‌طور؟** موجودی، تنها سقف است؛ سهمیهٔ ماهانه یک «پرکردن» است نه سقف دوم. این تصمیم جلوی باگ «توکن خریداری‌شده غیرقابل‌مصرف» را می‌گیرد.

## اسلاید ۸ — پرداخت، مالکیت و بازپرداخت

**یک اینترفیس، دو آداپتور:** `start` · `referenceFromCallback` · `verify` · `refund` — زرین‌پال و استرایپ.

```
محاسبهٔ مبلغ سمت سرور
        ▼
تراکنش pending + orderId (AF-YYYYMMDD-XXXXXXXX)
        ▼
ریدایرکت به درگاه
        ▼
callback/webhook → تأیید با خود درگاه
   زرین‌پال: verify با authority + مبلغ
   استرایپ: HMAC روی raw body
        ▼
settleTransaction (تراکنش دیتابیس)
   success + refId → اعطای مالکیت/شارژ کیف پول
```

**تضمین‌ها:**
- پارامتر `Status=OK` به‌تنهایی پذیرفته نمی‌شود؛ فقط تأیید درگاه.
- callback تکراری `credited: false` برمی‌گرداند؛ `refId` یکتاست.
- تراکنش ناموفق با دلیل ذخیره می‌شود؛ رکورد معلق نمی‌ماند.
- بازپرداخت: درخواست → تأیید ادمین → `refund` درگاه → ابطال مالکیت؛ تکرارپذیر (idempotent).

## اسلاید ۹ — احراز هویت و امنیت

| موضوع | پیاده‌سازی |
| --- | --- |
| ورود | OTP پیامکی؛ نرمال‌سازی E.164 (فارسی/عربی/لاتین) |
| کد | HMAC-SHA256 روی `phone:code`؛ یک‌بارمصرف؛ ۵ تلاش؛ ۱۲۰ ثانیه؛ ۳۰ ثانیه فاصله؛ ۶ بار در ساعت |
| نشست | توکن مبهم، هش‌شده در DB، کوکی `httpOnly`، ۳۰ روز |
| کلید مدل | AES-256-GCM در DB؛ فقط ماسک به ادمین |
| محدودیت | شمارندهٔ پنجره‌ای در Postgres (Redis اختیاری) |
| مرورگر | CSP سخت، `X-Frame-Options`، `nosniff` |
| حریم | بدون افشای وجود حساب؛ شماره/آی‌پی در گزارش خطا ذخیره نمی‌شود |

**جزئیات سرورلس:** بدنهٔ خام درخواست نگه داشته می‌شود تا امضای وب‌هوک استرایپ بعد از parse باطل نشود.

## اسلاید ۱۰ — گیت‌وی AI (سرویس جدا)

```
مشتری ── HTTPS ──> FastAPI (عمومی)
                      │  شبکهٔ داخلی
                      ▼
                   LiteLLM (بدون پورت عمومی)
                      ├── OpenAI
                      ├── Anthropic
                      ├── Gemini
                      └── Ollama (محلی)
```

- دو مدل منطقی: `agent-pro` و `agent-basic`؛ مشتری هیچ‌وقت نام مدل، توکن یا هزینهٔ واقعی را نمی‌بیند.
- پاسخ فقط `{ reply, credit_remaining_percent }`.
- fallback زنجیره‌ای، circuit breaker، مهلت ۲۵ ثانیه، آخرین مسیر Ollama.
- فروش اعتبار دلاری با مارک‌آپ ۲.۵×؛ کسر اتمی و ثبت در یک تراکنش.

**وضعیت:** این سرویس ساخته و تست شده، اما **هنوز در مسیر چت فروشگاه قرار نگرفته**؛ چت فعلی از `ProviderConfig` (یک ارائه‌دهندهٔ سازگار با OpenAI) استفاده می‌کند. اتصال آن، قدم بعدی است.

## اسلاید ۱۱ — استقرار و عملیات

| مرحله | چه اتفاقی می‌افتد |
| --- | --- |
| Build | export seed → `prisma generate` → `migrate deploy` (فقط production) → `seed:content` → `tsc` → `vite build` → sitemap |
| Routing | `/api/(.*)` → `api/index.ts` با rewrite؛ پارامتر اضافه حذف می‌شود |
| 404 | لیست صریح مسیرهای SPA؛ بقیه 404 واقعی |
| DB | Prisma `engineType=client` + `@prisma/adapter-pg`؛ بدون باینری Rust |
| مانیتور | `check-deploy.mjs` با ۱۲ بررسی، هر ۳۰ دقیقه |
| خطا | گزارش خطای مرورگر در `ClientError` با fingerprint |

**محدودیت شناخته‌شده:** سقف ۶۰ ثانیهٔ Function؛ استریم طولانی‌تر قطع می‌شود.

## اسلاید ۱۲ — کیفیت، تست و شکاف‌ها

**تست و گیت:**
- ۵۸ تست API (Vitest): قیمت‌گذاری، امضای پرداخت، کیف پول، OTP.
- اسکریپت smoke: ۴۵ بررسی end-to-end با PSP/پیامک ساختگی.
- گیت‌های build: `check:i18n` · `check:catalog` · `check:routes` · `typecheck`.
- ۱۲ بررسی استقرار روی نسخهٔ در حال اجرا.

**شکاف‌های فعلی (صادقانه):**
- یک ارائه‌دهندهٔ فعال در چت؛ گیت‌وی چندارائه‌دهنده هنوز وصل نیست.
- بدون تحلیل رویداد/فراگیر (Sentry)؛ فقط گزارش خطای مرورگر.
- بازپرداخت، تأیید دستی ادمین دارد.
- بدون آپلود فایل/RAG؛ پرسونا متنی است.
- صفحات کاتالوگ سمت کلاینت رندر می‌شوند؛ پیش‌رندر برای سئو در نقشهٔ راه است.
- سقف ۶۰ ثانیهٔ استریم روی پلن فعلی Vercel.

## جمع‌بندی در پنج خط

1. **فروشگاه و موتور اجرا** در یک محصول: کاتالوگ، خرید، کیف پول، چت، پنل.
2. **همه‌چیز سمت سرور:** پول، مالکیت، مصرف و کلید مدل؛ کلاینت فقط نمایش می‌دهد.
3. **مصرف قابل حسابرسی:** هر پاسخ، `UsageEvent` دارد و از کیف پول کسر می‌شود.
4. **پرداخت محافظه‌کار:** تأیید با درگاه، تسویهٔ تکرارپذیر، بازپرداخت قابل ردیابی.
5. **سرورلس‌محور:** Postgres تنها منبع حالت؛ بدون فایل محلی و بدون cron واجب.
